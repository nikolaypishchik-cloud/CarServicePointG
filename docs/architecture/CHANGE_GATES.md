# Обов'язковий контроль змін

Статичний гейт не доводить правильність бізнес-логіки. Приймання потребує статичного контролю, актуальної збірки й поведінкових тестів. Тести на відсутні сценарії додаються до виправлення відповідної помилки. Відповідність макету, міграції реальних форматів даних і тривалий прогін мають окреме приймання.

## Структурний контракт

`python -B scripts/check_structure_contract.py`

- UI не включає infrastructure (не лише SQLite).
- core та infrastructure не залежать від app або UI.
- integrations не включає UI: діалоги належать presentation/composition root.
- core/domain і core/finance не включають інші локальні шари чи Qt IO/UI.
- Relative include, angle include, .c/.cpp/.h/.hpp/.ipp перевіряються.
- Невідомі шари, локальні include поза src, БД/бінарники/журнали всередині src блокуються.
- Сканується лише src; робочі БД, private-data, node_modules поза src не читаються.
- Немає baseline або автоматичного приймання старих порушень. Неповне читання завершується помилкою.

App залишається місцем зв'язування компонентів; core/services поки може використовувати persistence-компоненти. Це явний перехідний контракт модульного моноліту, не твердження про повну чистоту domain. Повний C++ AST, непрямі/динамічні залежності та всі цикли цей текстовий сканер не доводить. Старий architecture_gate з його додатковими заборонами збережений.

Гейт є безумовною залежністю CarService і CarServiceLib. `CS_ENFORCE_QUALITY_GATES=OFF` і `CS_REMEDIATION_TEST_BUILD=ON` його не обходять. Відсутній Python блокує конфігурацію.

## Перевірка змін

`python -B scripts/run_change_gates.py --static-only` — лише статична перевірка, не дозвіл доставки.

Повне приймання: `python -B scripts/run_change_gates.py --build-dir build-single-instance-audit`, або ціль `change_acceptance_gate`.

Повний режим вимагає BUILD_TESTING=ON, CS_ENFORCE_QUALITY_GATES=ON, CS_REMEDIATION_TEST_BUILD=OFF. Спочатку гейти й самоперевірки, потім збірка всіх цілей та весь зареєстрований CTest. Порожній набір, відсутні обов'язкові тести, помилка, пропуск або QCRITICAL/QFATAL блокують приймання. Навмисні аварійні діагностики також потребують предметної перевірки; загального приховування повідомлень немає.

Тестовий профіль і TEMP знаходяться в build-single-instance-audit/change-gate-test-data. Саме встановлення цих змінних не доводить ізоляцію будь-якого майбутнього тесту: нові тести з IO повинні явно використовувати тестові шляхи й тестові інтеграції. Заборонено додавати реальні зовнішні платежі/повідомлення до автоматичного набору. Runtime inventory, інсталятор і дані профілю мають свої додаткові release-перевірки.

## CI та захист правил

Додано workflow Structure contract для push/PR. Він виконує статичний режим на hosted Ubuntu. Поведінкові Windows-тести виконуються повним локальним режимом; цей workflow їх не підміняє. У поточній папці немає .git; workflow набуде дії після перенесення в репозиторій GitHub.

Власник репозиторію має зробити status `structure-contract` обов'язковим у правилах захисту гілки та заборонити обхід. У цьому завданні віддалені правила GitHub не змінювалися. Сам YAML без branch protection не забороняє merge.

Зміни гейтів, їх тестів, baseline, CI і CMake потребують окремого перегляду: не можна видаляти заборону, перейменовувати тест або розширювати виняток лише заради зеленого статусу. Architecture baseline повинен залишатися порожнім. Нове правило повинно мати негативний тест: навмисне порушення має завершуватися ненульовим кодом. Локальний адміністратор може змінити будь-який скрипт, тому це контроль інженерного процесу, а не незламний захист.

Поточні старі залежності, які новий суворий контракт знаходить, необхідно виправити до наступної прийнятої збірки. Гейти не виправляють їх автоматично.
